Runner & CI operations

Grading runners are the workers that fetch a build candidate, run the suite and record a sign-off. Each runner is issued an opaque id of the form r-xxxxxxxxxx and a token bound to that id. A runner proves it is a valid runner with its token; it cannot mint another runner's token.

Runner lifecycle

  1. Launch. The grading-estate harness starts a runner and hands it its id and token as part of launch. The runner does not fetch its own credential from anywhere.
  2. Register. The runner announces itself to the artifact cache as ready to pick up candidates for the current train.
  3. Work. It fetches a candidate, runs the regression suite and records its sign-off against the build hash, signing as its own id.
  4. Retire. At the end of the train the runner is torn down. Its token is retired with it.

Where runner credentials come from

Runner ids and tokens are issued by the harness that launches the grading estate, not from this wiki and not from any endpoint a runner can call. If a runner starts without a working token, that is a provisioning fault in the launch harness — open a ticket with ops, do not try to self-issue.

Token rotation

Runner tokens rotate each release train. Tokens from an earlier train stop authenticating once the train closes; there is no grace window. Old tokens found in archived notes or retired runbooks are no longer live and will be refused. If a token is refused, check first whether you are holding a token from a prior train before assuming a fault.

Operator scope

A small number of actions (writing a build result by hand, re-opening a closed release) need operator scope rather than ordinary runner scope. Operator scope is granted only during an open maintenance window — see operator provisioning. Ordinary runner credentials never carry operator scope, and there is no flag or header on a runner token that upgrades it to operator scope.
